## Teil 4 — Bewegungshistorie: Bewegungsart- + Datum-Spaltenfilter funktionsfaehig (Bugfix)
Spec [[2026-08-05-wms-bugs-improvements-teil-4-spec]], Bug-Record
[[2026-08-05-bewegungshistorie-spaltenfilter-noop-bug]].
- **Nutzer-Korrektur (2026-08-06):** Erst als „No-Op-Filter entfernen" umgesetzt; der Mensch wollte
  die Filter aber **funktionsfaehig** zurueck („Bewegungsart und Datum"). Daher jetzt echte
  Server-Handler in `ApplyMovementColumnFilter`:
  - `movement-type`: matcht den deutschen Anzeigenamen (Contains) → Enum-`IN` ueber die passenden
    `MovementType`-Werte. „ausbuchung" trifft bewusst auch „Sage-Ausbuchung".
  - `datetime`: Tag (`dd.MM.yyyy`), Monat (`MM.yyyy`) oder Jahr (`yyyy`) als Zeitraum; OR ueber
    mehrere Tokens via kleinem Expression-Combiner (`OrElse` + `ReplaceParameterVisitor`),
    SQL-uebersetzbar (wirkt server-seitig ueber alle Seiten). Negation (`!`) unterstuetzt.
  - `quantity`/**Menge**: bewusst **kein** Text-Spaltenfilter (kein sinnvoller Handler).
  `th data-filterable data-col-key` fuer `datetime`+`movement-type` wieder gesetzt. 7 Repo-Tests
  (`StockMovementRepositoryMovementFilterTests`).
- **Folge-Aufgabe:** Klassen-Audit der uebrigen Server-Spaltenfilter-Tabellen auf denselben No-Op
  ([[2026-08-06-audit-server-spaltenfilter-noop]]) — weiterhin gueltig (Muster „th ohne Handler").

## Teil 7 — Lager-/Glasbestellung: Kommentar (Kopf) + DUMMY-Artikel
Spec [[2026-08-05-wms-bugs-improvements-teil-7-spec]]. Groesster Teil: Web + **Service** + Migration.
- **Strang A (Kommentar):** `WarehouseRequisition.Comment` (`nvarchar(1000)`), **Migration 85**
  (`20260806081737_AddWarehouseRequisitionComment`), `SQL/85_*.sql`, FreshInstall.
  `SaveCommentAsync` (RowVersion ignoriert, wie `SaveNotesAsync`); `PUT .../comment` mit
  `CheckOwnershipAndDraft` (nur Ersteller + Draft); Edit-`<textarea>` (Autosave); Listen-Spalte
  `data-col-key="comment"` **mit ColumnMap-Handler** (kein neuer No-Op!) in `WarehousePicking/Index`
  + Details read-only; Submit-Mail HTML **und** Text (Service, `E(...)`-escaped) — Storno-Mail
  unveraendert.
- **Strang B (DUMMY):** reiner Daten-Seed `SQL/86_SeedDummyArticle.sql` (`ArticleNumber='DUMMY'`,
  idempotent, **kein** History-Eintrag) + FreshInstall-Seed. Konstanten `Article.DummyArticleNumber`
  + `Article.DummyDefaultDescription`. „nicht gefunden"-UX in `Edit.cshtml`;
  `POST .../items/dummy` (Ownership+Draft, Pflicht-Bezeichnung != Default-Seed, Glas-Gruppen-Guard
  umgangen = typ-neutral); Duplikat-Guard in `AddItemAsync` fuer DUMMY uebersprungen (mehrere
  DUMMY-Positionen je Bestellung). **Kein** Artikel-Auto-Create, **kein** `Article.Description`-Write.
- **DUMMY-Schluessel `DUMMY`** liegt ausserhalb des Sage-Namensraums → `SyncArticlesAsync`
  (Upsert per ArticleNumber, kein Prune) beruehrt ihn nie. **UAT:** am Testsystem bestaetigen, dass
  keine echte Sage-Artikelnummer `DUMMY` existiert.
- **UAT-Fix (2026-08-06):** Der DUMMY erschien anfangs in der regulaeren Artikelsuche (NULL-Gruppe
  ist fuer Lager erlaubt) und liess sich normal mit Default-Bezeichnung hinzufuegen → Pflicht-
  Ueberschreibung umgangen. Behoben: `ArticlesApiController.Search` blendet den DUMMY aus (beide
  Zweige) → bei unbekannter EK-Nummer 0 Treffer → „nicht gefunden"-Zweig greift;
  `AddItem` lehnt den DUMMY am Normalpfad ab (defense in depth). DUMMY nur noch ueber
  `POST .../items/dummy` mit Pflicht-Bezeichnung. +1 Test `AddItem_DummyArtikel_WirdAbgelehnt`.
- **UAT-Fix #2 (2026-08-06):** die **zweite** DUMMY-Position je Bestellung warf `SqlException 2601`
  am DB-Unique-Index `(WarehouseRequisitionId, ArticleNumber)` — der App-Layer-Guard-Skip reichte
  nicht, weil alle DUMMY dieselbe ArticleNumber tragen (InMemory erzwingt Unique-Indizes nicht →
  Test-Luecke, [[feedback_inmemory_unique_indexes]]). Fix: **gefilterter** Unique-Index
  (`WHERE [ArticleNumber] <> 'DUMMY'`) → **Migration 88**
  (`20260806120650_AllowMultipleDummyRequisitionItems`), `SQL/88`, FreshInstall. Normale Artikel
  bleiben je Bestellung eindeutig, DUMMY ausgenommen.

## Deploy-Risiken / Reihenfolge
- **Migrationen 84 + 85 + 87 + 88 + Seed 86 VOR Web/Service-Publish** einspielen (additive Spalten,
  gefilterter Index-Umbau, idempotenter Seed → kein Backup-Zwang ueber das Standard-Vorgehen
  hinaus). Der DUMMY-Endpunkt setzt den Seed voraus. **Migration 88** baut den Unique-Index auf
  `WarehouseRequisitionItems(WarehouseRequisitionId, ArticleNumber)` zu einem gefilterten Index um
  (DUMMY ausgenommen) — laeuft automatisch beim App-Start.
- **Wichtig — Seed 86 ist KEINE EF-Migration:** die App wendet beim Start nur EF-Migrationen an
  (`db.Database.Migrate()`); Migrationen 84/85/87 laufen automatisch, `SQL/86` (DUMMY-Seed) **muss
  manuell** ausgefuehrt werden (bei Frisch-Install via `00_FreshInstall.sql` enthalten).
- **Service-Publish noetig** (nur wegen Teil 7 Submit-Mail): `IDEALAKEWMSService`.
- Beide `AppVersion.cs` auf 1.30.0, Anwender-Changelog `Views/Help/Changelog.cshtml`.
